# Detailed Analysis of hardn_suricata_tune_performance Function

**This is an example taken from [suricata.sh](https://github.com/OpenSource-For-Freedom/HARDN-XDR/blob/STIG/src/setup/modules/suricata.sh)

The `hardn_suricata_tune_performance()` function utilizes a sophisticated system
for resource optimization routine, that dynamically configures Suricata
IDS/IPS, based on the host system's available resources.
key components:

## 1. Resource Detection

The function begins by detecting the system's available resources:

```bash
local mem_total
mem_total=$(free -m | grep Mem | awk '{print $2}')
local cpu_count
cpu_count=$(nproc)
```

- `free -m` retrieves memory information in megabytes
- `grep Mem` filters for the total memory line
- `awk '{print $2}'` extracts just the memory value
- `nproc` gets the number of available processing units (CPU cores)

## 2. Memory Tiering System

The function implements a tiered approach to memory configuration:

```bash
local mem_tier
if (( mem_total > 8000 )); then
    mem_tier="high"
elif (( mem_total > 4000 )); then
    mem_tier="medium"
elif (( mem_total > 2000 )); then
    mem_tier="low"
else
    mem_tier="minimal"
fi
```

This creates four distinct memory tiers:
- **High**: Systems with >8GB RAM
- **Medium**: Systems with 4-8GB RAM
- **Low**: Systems with 2-4GB RAM
- **Minimal**: Systems with <2GB RAM

## 3. Memory-Based Configuration Parameters

For each memory tier, the function assigns specific values to critical Suricata packet processing parameters:

```bash
case "$mem_tier" in
    "high")
        ring_size=65536
        block_size=65536
        max_pending_packets=4096
        ;;
    # Other tiers...
esac
```

These parameters control:
- **ring_size**: The size of the packet capture ring buffer (larger values reduce packet drops under high load)
- **block_size**: The size of memory blocks for packet capture (affects memory efficiency)
- **max_pending_packets**: Maximum number of packets waiting to be processed (prevents memory exhaustion)

The values scale proportionally with available memory, ensuring optimal performance without exhausting resources.

## 4. CPU Tiering System

Similar to memory, the function categorizes CPU resources into tiers:

```bash
local cpu_tier
if (( cpu_count > 8 )); then
    cpu_tier="many"
elif (( cpu_count > 4 )); then
    cpu_tier="several"
else
    cpu_tier="few"
fi
```

This creates three CPU tiers:
- **Many**: Systems with >8 cores
- **Several**: Systems with 5-8 cores
- **Few**: Systems with ≤4 cores

## 5. CPU Affinity Optimization

The most sophisticated part of the function is the CPU affinity configuration, which assigns specific tasks to specific CPU cores:

```bash
local mgmt_cpus='[ "0" ]'  # Management tasks
local recv_cpus='[ "1" ]'  # Packet receive tasks
local worker_cpus          # Packet processing workers
```

For each CPU tier, it implements a different strategy:

### "Many" Cores (>8)
```bash
mgmt_cpus='[ "0" ]'
recv_cpus='[ "1" ]'
# Dynamic worker CPU allocation
local max_workers=$((cpu_count > 8 ? 6 : cpu_count-2))
```

- Core 0: Reserved for management tasks
- Core 1: Dedicated to packet reception
- Cores 2-7 (or fewer): Used for worker threads
- The function intelligently caps worker threads at 6 even on systems with many cores
- This prevents Suricata from consuming all system resources

The worker CPU allocation uses a loop to dynamically build a JSON-style array of CPU IDs:
```bash
for ((i=2; i<max_workers+2 && i<cpu_count; i++)); do
    worker_cpus+=""$i""
    if (( i < max_workers+1 )) && (( i < cpu_count-1 )); then
        worker_cpus+=", "
    fi
done
```

### "Several" Cores (5-8)
```bash
mgmt_cpus='[ "0" ]'
recv_cpus='[ "1" ]'
worker_cpus='[ "2", "3" ]'
```

- Core 0: Management tasks
- Core 1: Packet reception
- Cores 2-3: Worker threads
- This leaves some cores free for other system processes

### "Few" Cores (≤4)
```bash
if (( cpu_count >= 3 )); then
    mgmt_cpus='[ "0" ]'
    recv_cpus='[ "1" ]'
    worker_cpus='[ "2" ]'
else
    # For 1-2 core systems
    mgmt_cpus='[ "all" ]'
    recv_cpus='[ "all" ]'
    worker_cpus='[ "all" ]'
fi
```

- For 3-4 cores: Minimal but still dedicated core assignment
- For 1-2 cores: Disables CPU affinity completely with `"all"` setting
- This prevents performance degradation on low-core systems

## 6. Configuration File Generation

The function generates a comprehensive YAML configuration file with all optimized settings:

```bash
cat > "$tuning_file" << EOF
# Suricata performance tuning
# Generated by HARDN-XDR
# System: ${mem_total}MB RAM (${mem_tier} profile), ${cpu_count} CPU cores (${cpu_tier} profile)

af-packet:
  - interface: default
    # ... packet capture settings

threading:
  set-cpu-affinity: yes
  cpu-affinity:
    # ... CPU affinity settings

detect:
  # ... detection engine settings

app-layer:
  protocols:
    # ... protocol-specific memory limits
EOF
```

Notable aspects:
- The configuration includes detailed comments about the system profile
- Memory limits for HTTP and SMTP protocols are dynamically calculated based on available RAM
- HTTP request/response limits: 1/20th of total RAM
- SMTP extraction limits: 1/40th of total RAM

## 7. Configuration Integration

Finally, the function ensures the performance configuration is included in the main Suricata configuration:

```bash
if ! grep -q "include: suricata-performance.yaml" /etc/suricata/suricata.yaml; then
    echo "include: suricata-performance.yaml" >> /etc/suricata/suricata.yaml
    # ...
fi
```

## Summary of Optimization Strategy

This function implements a sophisticated multi-tiered approach to Suricata performance optimization:

1. **Resource Detection**: Dynamically identifies available system resources
2. **Tiered Configuration**: Categorizes systems into capability tiers
3. **Memory Optimization**: Scales buffer sizes and packet limits based on available RAM
4. **CPU Optimization**: Implements intelligent core allocation strategies
5. **Dynamic Limits**: Calculates protocol-specific memory limits proportionally to system resources

The overall strategy balances maximum performance with system stability,
ensuring Suricata runs efficiently across a wide range of hardware
configurations from minimal VMs to high-performance servers.
